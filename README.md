# CLO — CloudLabelOntology

An OWL 2 ontology, a resource-type catalogue and a diagnosis-and-repair cycle for
**provider-agnostic governance of cloud resource labels (tags)**. The company
labelling standard is *derived* from the needs of governance roles (FinOps,
Security, Operations, ...), team conventions become observable, and absence is
only concluded where the provider response shows that a record is complete.

Version 9.2 · Apache-2.0 · namespace `http://example.org/clo/ontology/clo#` (anonymised for review; the camera-ready release restores the persistent IRI)

| | |
|---|---|
| T-Box | 1,380 triples (English annotations only), 110 classes (22 defined), 28 object / 35 datatype properties, 8 + 3 property chains; OWL 2 DL (ROBOT), not RL (9 axioms, `data/profile_RL.txt`) |
| Catalogue | 165 types from Fix Inventory + 10 types added from the open corpus (`ontology/clo_types_ext.ttl`); labelling support curated with source URLs |
| Run time | `rules/materialise.ru` (19 equality-free SPARQL rules, = HermiT/Pellet on the operative entailments E) + 15 closed-world SPARQL rules in `rules/cwa/` + 3 in `clo/audit.py` |
| Demo | **CLO Studio** (`tools/clo_demo.py` → `examples/demo/clo_studio.html`): what-if switches, role lens, the derivation of every finding, repairs, compiled artefacts, loop and corpus results |
| Evaluation | differential testing against an independent oracle, planted defects matched per key, an open corpus of 1,686 resources recorded from AWS/Azure/GCP with a witness check of the completeness rules, AWS Config/Azure Policy/GCP constraints, Cloud Custodian and three OPA baselines against two ground truths, four reasoners, end-to-end cycle cost, a repair-sensitivity sweep and a closed-loop simulation |

## CLO Studio in 30 seconds

Open `examples/demo/clo_studio.html` in a browser (no server, no installation, works offline).
Video walkthrough (3 min): `demo/clo_studio_demo.mp4`. Rebuild the page from the pipeline with `make demo`,
or with Docker:

```bash
docker build -t clo . && docker run --rm -p 8000:8000 clo     # then open http://localhost:8000/clo_studio.html
```

## Quick start

```bash
pip install -r requirements.txt          # Python 3.11+, Java 8+ for HermiT
make test                                # ontology (HermiT), organisational module, pipeline, competency questions
python3 tools/clo_audit.py --out-dir out                 # one cycle on the company example
python3 tools/clo_compile.py --in-dir out --out-dir out/enforce   # AWS Config / Azure Policy / Custodian
python3 tools/clo_viz.py --in-dir out --out out/clo_view.html     # graph explorer
make demo                                # CLO Studio: examples/demo/clo_studio.html (open in a browser)
```

Tested with Python 3.13, Owlready2 0.51 (HermiT 1.3.8), pyoxigraph 0.5.11, rdflib 7.6,
owlrl 7.6.2, regopy 1.5.2, c7n 0.9.53 and OpenJDK 21. Pellet: Owlready2 0.51 bundles a
Jena built for Java 25; with an older JVM install `requirements-pellet.txt` in a
second environment and set `CLO_PELLET_PYTHON` to its interpreter.

## Reasoning design

* **DL at design time.** The T-Box, the catalogue and the organisational module are
  OWL 2 DL and are checked with HermiT and ROBOT.
* **Rules at run time.** `rules/materialise.ru` is the rule form of the operative
  axioms (chains C-1..C-11, transitivity, the sufficient direction of the defined
  classes), applied to a fixpoint in Oxigraph. `eval/engines.py` and `tests/test_v9.py`
  check that it returns exactly HermiT's and Pellet's operative entailment set E.
* **No equality at run time.** OWL has no unique-name assumption: in 8.x a functional
  `ownedBy` made HermiT silently merge two teams owning one resource. Two owners (I-27),
  two types (I-28) and duplicate records are closed-world findings or are removed at
  ingestion; CLO-R never derives `owl:sameAs`.
* **Local closed world.** Absence-based rules (I-07, I-11, I-21, I-26) run only on
  `clo:recordComplete true` records; `tools/ingest_c7n.py` derives the flag from the
  response shape (rules A1-A3, Z1, G1, N in its header).

## Teams, roles and repairs

`servesRole ∘ needsLabel ⊑ requiresLabel` (C-9) derives the standard;
`ownedBy⁻ ∘ hasLabel ∘ hasLabelKey ⊑ usesKey` (C-10) observes team practice;
`ownedBy ∘ governedBy ⊑ governedBy` (C-11) applies team policies. Repairs follow a
fixed order — rename a variant to the canonical key, inherit from a `partOf` parent,
the account's or the team's dominant value (>= 80 % of >= 2 uses) where the key's
`clo:valueSource` allows it, else ask the owner. `data-classification` has no value
source and is never guessed.

## Reproducing the paper

```bash
git clone https://github.com/cloud-custodian/cloud-custodian ../cloud-custodian   # commit 8bf784b
make ingest C7N=../cloud-custodian      # data/open/ (already included)
make reproduce                          # all of results/ (several hours: HermiT and Pellet)
make reproduce-fast                     # everything but the DL runs and the fixture checkout (~30 min)
make tables PAPER=../paper              # numbers.tex and tab_*.tex
```

## Limitations

* No production estate yet; the open corpus comes from Cloud Custodian's test accounts (its tags were written
  by tests, e.g. `maid_status`), so it validates response shapes and spellings, not compliance.
* The completeness rules are checked against other observations in the same recorded test (an upper bound on
  their error, since tests change tags), not against live accounts.
* Repair accuracy depends on how regular the estate is (`eval/repair_sensitivity.py`).
* I-15's orchestrator exemption and the synonym groups were adjusted on the open corpus.
* The baselines are our encodings of each tool's documented semantics; Custodian's and
  OPA's own evaluators are executed, AWS Config and Azure Policy are emulated.
* Two of the 13 categories (Monitoring, Analytics) have no BaseKind; no type is `partial`.
* Neo4j/Cypher forms of three rules (`examples/audit.cypher`) are not tested against a live
  instance.
